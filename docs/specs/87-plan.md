# Plan: Sign-in: send codes by email, then re-check code autofill on a real phone

Issue: #87 · Spec: [87.md](87.md) · Runs on: `cloud, then mac` · Status: waiting for gate 2

## Contracts

No change to a shared schema, no new endpoint, no migration, and no change in `packages/shared`.

- **`POST /auth/code`.** Request, `204` and `400`/`429` stay as they are. New: when the email provider rejects the send or cannot be reached, it answers `500`. The body is Fastify's default one, `{"statusCode":500,"error":"Internal Server Error","message":"Could not send the sign-in code"}` (checked by running a handler that throws), where `message` is a fixed text written by the sender and never provider text. It is not an `ErrorResponse`, and the shared client does not need it to be: `errorResponseSchema` has no `"Internal Server Error"` value, so `createApiCall` already reads this body as `unavailable`, and web and mobile show the existing "unavailable" copy.
- **Environment.** API: `RESEND_API_KEY`, optional. An empty value counts as unset, because `.env.example` will carry the name empty and `cp` of it must keep the log sender. Web: `ALLOWED_DEV_ORIGINS`, optional, comma-separated hostnames, read when the config loads. Neither is required anywhere.
- **Internal interface.** `AuthDeps["sendSignInCode"]` keeps its signature `(email, code, log) => Promise<void>`. A new `createResendCodeSender({ apiKey, fetch, timeoutMs? })` returns that function. A new `signInCodeSenderFor(env, fetch)` returns the Resend sender when the key is set and `logSignInCode` otherwise.
- **Resend's request.** `POST https://api.resend.com/emails`, `authorization: Bearer <key>`, JSON body `{ from, to: [email], subject, text }`, success on any 2xx. This is Resend's API as I know it. I could not read its documentation from this session (resend.com is outside the session's allowed network), so the shape is unverified until the phone check sends a real email.

## What the code does today

Read in full: `apps/api/src/auth/routes.ts`, `log-code-sender.ts`, `log.test.ts`, `dev-codes.ts`, `apps/api/src/app.ts`, `server.ts`, `env.ts`, `db/database-env.ts`, `apps/api/.env.example`, `apps/web/next.config.ts`, `apps/web/vitest.config.ts`, `packages/shared/src/api-client.ts`, `packages/shared/src/auth.ts` (the `errorResponseSchema` and `SIGN_IN_CODE_TTL_MS`), `README.md`, `.gitignore` and `docs/evidence/67/check.md`.

- **The sender is already a dependency.** `registerAuthRoutes` takes `sendSignInCode` and awaits it after `issueCode` has stored the code hash. Only `server.ts` names `logSignInCode`. `buildApp` wraps the sender when dev codes are on, so `DEV_SIGN_IN_CODES` keeps working with either sender.
- **The route has no catch.** A throwing sender gives Fastify's default `500`, whose `message` is the thrown error's message. That is why the sender must throw a fixed message: a provider error text in it would reach the response and the log. The issued code stays in the store (spec assumption) and counts toward the 5 codes per 15 minutes.
- **Env.** `env.ts` extends one schema per concern (`devCodesEnvSchema` in `dev-codes.ts`, tested on its own). `env.ts` itself parses `process.env` when imported, so the new schema goes in its own module, as `devCodesEnvSchema` does. `database-env.ts` calls `process.loadEnvFile()`, which reads `.env` from the working directory and does not replace variables that are already set. `.gitignore` has `.env`, which matches `apps/api/.env`.
- **Web config.** `next.config.ts` has `cacheComponents`, `partialPrefetching` and `transpilePackages`, and no `allowedDevOrigins`. The Next docs (`allowedDevOrigins.md`) say entries are hostnames only, with no scheme and no port, and that `localhost` and the host the server started with are always allowed. Vitest in `apps/web` runs only `src/**/*.test.ts`.
- **Readers of the log sender's promise.** `grep -rn "no email yet\|API log\|writes each sign-in code" README.md CLAUDE.md apps` finds `README.md` lines 17, 20 and 21, `CLAUDE.md` line 42 (the Sign-in rule), the comment in `log-code-sender.ts` line 4 and the doc comment on `sendSignInCode` in `routes.ts` line 18. `docs/evidence/67/check.md` also says the API does not deliver codes yet; it is a dated record and stays.
- **Tests to model on.** `log.test.ts` (a whole sign-in with the log captured through a `Writable`), `routes.test.ts` (`setup()` with a sender that records codes) and `dev-codes.test.ts` (env schema tests).
- **E2E.** `playwright.config.ts` starts the API with an `env` block that sets `NODE_ENV=test`, `DEV_SIGN_IN_CODES=true` and `AUTH_SECRET`, and `apps/mobile/e2e/run.sh` does the same. Neither sets `RESEND_API_KEY`. See the second question below.
- **Open PRs.** `gh api repos/{owner}/{repo}/pulls` returns none, so nothing else touches these files.

### The email, for gate 2

The spec leaves the exact wording to this plan. Subject and plain-text body, with the code on its own line and the lifetime taken from `SIGN_IN_CODE_TTL_MS`, so the text cannot drift from the real 10 minutes:

```text
Subject: Mã đăng nhập Góp của bạn

Mã đăng nhập Góp của bạn là:

123456

Mã có hiệu lực trong 10 phút. Nếu bạn không yêu cầu mã này, hãy bỏ qua email này.
```

## Risks

- **Questions for the author.** Answer these before adding `plan-ok`; the build reads the answers.
  1. **The email wording above: is it right?** The spec leaves it to the plan. A related risk: iOS recognises codes by cues in the message, and I am not sure it does so for a Vietnamese-only text. If iOS offers nothing in step 6 (after the HTTPS retry), the first thing to try is one more line with a cue in English, for example `Your Góp sign-in code: 123456`. Do you want that line in from the start? It costs nothing now, and avoids a second phone check.
  2. **Add `RESEND_API_KEY: ""` to the API's environment in `playwright.config.ts` and in `apps/mobile/e2e/run.sh`?** The spec keeps the e2e runs on the log sender. But `process.loadEnvFile()` reads `apps/api/.env` and does not replace variables that are already set. With your key in that file, a web or mobile e2e run on the Mac would start the API with the Resend sender, and its throwaway `example.test` addresses would be rejected, so every sign-in would fail. An empty value stops the file from filling it in. It is a one-line change in each file, and it is not in the spec, so the plan leaves it out unless you say yes. Without it, step 6 says to take the key out of `apps/api/.env` before any e2e run, and the key lives there only during the phone check.
- **Resend's API shape is from memory.** I could not read its documentation from this session. A mismatch (a different field name, a header) shows up only when a real email is sent, which is step 6, after the cloud steps are merged-ready. The unit tests pin my reading of the API. If the first real send gets a `4xx`, the log shows the status, and the sender is the one file to fix.
- **A failed send still uses up a code.** As the spec says, the issued code stays and counts toward the 5 codes per 15 minutes. A provider outage can stop a member from asking again for up to 15 minutes. It does not leave a usable code unseen: the code is hashed and nobody has it.
- **`resend.dev` delivers only to the key owner's address.** With the key set, a sign-in with any other address fails with the generic error. That is expected here, and it is why the key is used only during the phone check.
- **The spec's AC 3 and AC 4 are security-relevant but not tagged `[security]`.** Step 3 tests them on their own anyway. I suggest tagging them at the next spec revision.
- **The label says `cloud`; the plan ends on `mac`.** Steps 1 to 5 are `cloud`, step 6 is the owner's, with a real phone. `/factory-build 87` will finish the cloud steps and then stop with a handover.
- **Rollback.** Revert the commits, or leave `RESEND_API_KEY` unset: the log sender is then used, as today. The web change does nothing when `ALLOWED_DEV_ORIGINS` is unset. No data or migration is touched.

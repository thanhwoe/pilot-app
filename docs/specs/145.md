# API: a member can delete an expense they paid

Issue: #145 · Runs on: `cloud` · Status: waiting for gate 1

## User story

As a member of a group, I want to delete an expense I paid, so that a wrong or duplicate expense stops counting in the group's expense list and balances.

## Acceptance criteria

1. Given a group with members A and B, and an expense paid by A
   When A calls `DELETE /groups/:id/expenses/:expenseId`
   Then the answer is 204 with no body, and the expense is gone

2. Given an expense paid by A that A has deleted
   When any member lists the group's expenses and asks for its balances
   Then the expense isn't in the list, and the balances and suggested payments are those of the group without it (for the only expense of 100000 split equally, A and B are back at 0 with no suggestions)

3. [security] Given an expense paid by A
   When B, another member of the same group, calls the DELETE
   Then the answer is 403 `forbidden`, and the expense is still listed and still counted in the balances

4. [security] Given a user who is not a member of the group, a group that doesn't exist, or a malformed group id
   When they call the DELETE
   Then the answer is the same 404 `not_found` for all three, and no expense is deleted

5. Given a member of the group
   When they delete an expense id that doesn't exist, is malformed, belongs to another group, or was already deleted
   Then the answer is 404 `not_found`, and no expense in any group changes

6. [security] Given a call with no session, or with an ended or unknown session
   When it calls the DELETE
   Then it gets 401 `unauthorized`, and nothing is deleted

## Assumptions

1. "The member who paid it" is the expense's payer, because the API stores no other "who recorded it", and an expense can be paid by someone other than the caller.
2. The delete is permanent, because the owner chose it; the list and the balances read the stored expenses, so they need no change.
3. Success is 204 with no body, because there is nothing to return; error bodies use the shared error schema, which gains `forbidden`.
4. An expense of another group, a malformed id and an unknown id all answer the same 404 `not_found`, as a malformed group id does, so a caller learns nothing about other groups' expenses.
5. The checks run in this order: session (401), group and membership (404), expense in that group (404), then that the caller is the payer (403). The 403 tells a member the expense exists; they already see it in the group's list, so nothing leaks.
6. A second DELETE of the same expense answers 404, not 204, because the expense no longer exists.
7. The expense and its shares go together: no share of a deleted expense remains, and a failure leaves the expense whole.

## Out of scope

- Any web or mobile screen, button or API-client call for deleting.
- Editing an expense, undoing a delete, a deleted-expenses list or an audit trail.
- Letting the group's creator, or anyone but the payer, delete an expense.
- Changing how expenses are added, listed or how balances are computed.

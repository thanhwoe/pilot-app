# Expenses: add and list expenses with an equal split, on the API

Issue: #95 · Runs on: `cloud` · Status: waiting for gate 1

## User story

As a member of a group, I want to record an expense that I paid and split it equally, so that the group knows who owes what.

## Acceptance criteria

1. Given a group with members A, B and C
   When A adds an expense of 90000 VND for "Ăn tối", paid by A, split equally between A, B and C
   Then the answer is 201 with the expense, and it is stored with its payer, amount, description and three shares of 30000 VND

2. Given an amount that doesn't divide evenly, such as 100000 VND paid by A and split between A, B and C
   When the expense is added
   Then the shares are whole VND and add up to exactly the amount: each share is the amount divided by the number of members in the split, rounded down, and the remainder goes 1 VND at a time to the payer first (if in the split), then to the other members in the order they joined the group (`joined_at`, then `user_id` on a tie), so A gets 33334, B 33333 and C 33333

3. Given a split that leaves the payer out, such as 100000 VND paid by A and split between B and C only
   When the expense is added
   Then the shares are B 50000 and C 50000, and A has no share; and for 100001 VND the extra 1 VND goes to the member who joined first

4. Given a group with expenses
   When a member lists them
   Then they get every expense of that group and no other group's, newest first, each with its payer, amount, description, creation time and shares

5. Given a group with no expenses
   When a member lists them
   Then the answer is 200 with an empty list

6. Given an amount that is zero, negative, not a whole number, below 1 or above 100,000,000 VND; or a description that is empty or only spaces, or longer than 200 characters after trimming; or a split that is empty, repeats a member, or names a non-member; or a payer who is not a member
   When the expense is added
   Then it is rejected with 400 `invalid_request` and nothing is stored

7. Given an amount of exactly 1 VND, or exactly 100,000,000 VND, and a description of exactly 200 characters
   When the expense is added
   Then it is accepted

8. Given a description with spaces around it
   When the expense is added
   Then it is stored and returned without those spaces

9. [security] Given a user who is not a member of the group
   When they add or list its expenses
   Then they get the same 404 `not_found` as for an id no group has, nothing is stored, and the answer doesn't reveal whether the group exists

10. [security] Given a call with no session, or with an ended or unknown session
    When it adds or lists expenses
    Then it gets 401 `unauthorized`, checked before the body, and nothing is stored

11. Given a group id that is not a valid id
    When expenses are added or listed
    Then the answer is 404 `not_found`, as for a group that doesn't exist

## Assumptions

1. A member who isn't the payer may add an expense for another member, because the issue says "a member ... records an expense" and doesn't limit who pays. The payer must still be a member.
2. The split has at least one member, and each member appears once, because a share needs someone to hold it and a duplicate has no meaning in an equal split.
3. The split's order is the rule the owner fixed (payer first, then join order), not the order in the request, because the owner's answer on the issue sets it. The same result comes back whatever order the request lists the members in.
4. Both the add and the list calls use the routes, error shapes and session handling that groups already use (`invalid_request`, `unauthorized`, `not_found`), because the repo already settles them.
5. The expense gets its creation time from the server, and "newest first" means by that time, with a fixed tie-break so the order is stable, because the issue doesn't take a date from the client.
6. The amount maximum (100,000,000 VND) and minimum (1 VND) are shared constants beside `GROUP_NAME_MAX_LENGTH`, and the description maximum is 200 characters, as the owner answered on the issue.
7. The split function is pure and lives in `packages/shared` with unit tests, so balances (#96) and the mobile form (#97) use the same rule.

## Out of scope

- Edit and delete of an expense
- Exact-amount and share splits
- Balances (#96)
- Any web or mobile screen (#97)
- Dates chosen by the client, categories, currencies, receipts

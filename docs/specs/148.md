# Mobile: record a suggested payment as paid from the group screen

Issue: #148 · Runs on: `mac` · Status: waiting for gate 1

## User story

As a group member, I want to tap "Đã trả" on a suggested payment line (for example "Bạn trả X 20.000 ₫") on the group screen, so that the payment is recorded and the balances and payment lines update right away without leaving the screen.

## Acceptance criteria

1. Given a member views the group screen and a payment line "Bạn trả X 20.000 ₫" is shown
   When the screen renders
   Then that line shows a button with the text "Đã trả" (on both iOS and Android)

2. Given a member taps "Đã trả" on a payment line from them to member X for 20.000 ₫
   When the app calls the API settlement route
   Then the API responds 201 and stores a settlement with payer = the member, payee = X, amount = 20000, in that group

3. Given the settlement was recorded successfully
   When the response arrives
   Then the balances and payment lines on the same screen are refreshed, the user stays on the group screen, and the paid line no longer appears (or shows the reduced remaining amount if the balances say so)

4. Given a group where member A owes X 20.000 ₫ and no other debts exist
   When A's settlement of 20000 to X is recorded
   Then the shared balance function returns 0 for both A and X, and returns no suggested payments

5. Given the shared balance logic receives expenses and settlements
   When it computes balances
   Then the payer's balance increases by the settlement amount and the payee's balance decreases by the same amount, so the sum of all balances remains 0

6. Given the API receives a settlement request with an amount that is 0, negative or not a whole number
   When the request is validated
   Then the API responds 400 and stores nothing

7. Given the API receives a settlement request where payer and payee are the same member
   When the request is validated
   Then the API responds 400 and stores nothing

8. [security] Given a request to the settlement route without a valid session
   When the API handles it
   Then it responds 401 and stores nothing

9. [security] Given a signed-in user who is not a member of the group
   When they call the settlement route for that group
   Then the API responds 404, as the other group routes do for non-members, and stores nothing

10. [security] Given a settlement request where the payer or the payee is not a member of the group
    When the API validates it
    Then it responds 400 and stores nothing

11. Given the user taps "Đã trả" and the API call fails (network error or 5xx)
    When the failure is detected
    Then an error message is shown on the screen, the payment line remains with its "Đã trả" button, and no balances change

12. Given the user has tapped "Đã trả" and the request is still in progress
    When the user taps the button again
    Then no second request is sent (the button is disabled or shows a loading state) and only one settlement is stored

13. Given a group with no suggested payments
    When the group screen renders
    Then no "Đã trả" button is shown

14. [security] Given a signed-in member of the group
    When they call the settlement route with a payer who is not themselves
    Then the API responds 403 and stores nothing

15. Given a payment line where someone else pays (for example "X trả Y 20.000 ₫", neither of them the signed-in user as payer)
    When the screen renders
    Then that line shows no "Đã trả" button

16. Given the settlement was stored (201) and the refresh of balances then fails
    When the failure is detected
    Then the screen shows the balances error with its retry, and the "Đã trả" button is not offered again for that line until the balances load, so the same payment can't be stored twice

## Assumptions

- The button appears only on lines where the signed-in user is the payer, and the API accepts a settlement only when the payer is the caller (403 otherwise), because the issue's example is "Bạn trả X" and nobody should record a payment on another member's behalf.
- The route is `POST /groups/:id/settlements` and checks in the order the expense routes use: session (401), group and membership (404), then the body (400), then payer = caller (403).
- The API stores any positive whole VND amount and does not compare it with the current suggestion, so a stale line records what the user saw.
- Settlements are stored per group (group, payer, payee, amount, time) and the shared balance function takes them as an input beside expenses; the API and the mobile app use the same function and the same shared schemas.
- After a success, the screen reloads balances from the API and does no arithmetic of its own.
- When the balances reload fails after a stored settlement, the line's button stays hidden until the balances load again, because the 201 was stored and the lines on screen are stale (AC 16).
- The wording of the error and the in-progress state is the build's choice, kept in the shared copy.

## Out of scope

- Undo or deletion of a settlement.
- A settlement history screen or list.
- Notifying the other member, or confirmation by the receiving member.
- Entering a partial amount: the button records the amount shown on the line.
- Any change to the web app.
- Any change to how expenses or the equal split work.

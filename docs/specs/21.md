# Mobile: the groups list never retries or shows that it is loading

Issue: #21 · Runs on: `mac` · Status: waiting for gate 1

## User story

As a member on the mobile app, I want to see that my groups are loading, and to retry when they fail to load, so that a brief API outage doesn't leave the list broken until I restart the app.

## Acceptance criteria

1. Given the first groups load hasn't answered yet
   When the home screen shows
   Then the list area shows "Đang tải nhóm…", with no empty state and no connection error
2. Given the first load fails (API unreachable, a timeout or a 5xx)
   When it answers
   Then the connection error shows with a "Thử lại" button under it
3. Given the connection error is showing and the API is back
   When I tap "Thử lại"
   Then "Đang tải nhóm…" replaces the error and the button, and then my groups (or the empty state) show
4. Given the connection error is showing and the API is still down
   When I tap "Thử lại"
   Then the connection error and "Thử lại" show again
5. [security] Given the connection error is showing and my session has ended on the API
   When I tap "Thử lại" and the list answers 401
   Then the token is deleted from secure store and the sign-in screen shows, as in #19 AC 4
6. Given the list loaded fine
   When the home screen shows
   Then there is no "Thử lại" button, and the list reloads only after a create, as now

## Assumptions

- The loading line, the error and the button each have a `testID` for tests: `groups-loading`, `groups-error` (existing) and `groups-retry`.
- The loading text is the web's "Đang tải nhóm…". It moves into the shared groups copy as `loading`, next to `retry` ("Thử lại"), and the web uses the shared string in place of its own. The web's text does not change, because one string for both apps matches how the other groups copy is shared.
- Mobile only. The web already reloads the list on every page load, so it gets no retry and no other change.
- Several presses of "Thử lại" before the screen re-renders make one request, because #23 showed that a button disabled only on the next render lets a second fast press through.
- If a create finishes while a retry is still pending, the create reloads the list as it does now, and the answer to the load that started last is the one shown, because an older answer must not overwrite a newer list.
- A retry that answers after the user has signed out changes nothing, and a 401 in that answer does not delete the next sign-in's token (the `mounted` check from #19), because the stored token may by then belong to a new session.
- The create form stays usable while the list is loading, because a create during a pending load already works and reloads the list.
- The retry and loading states are tested with Jest home-screen tests in `apps/mobile/src/home.test.tsx`, because a Maestro flow can't stop the API partway through a flow or catch a brief loading line (found in #23). The existing Maestro groups flows must still pass on iOS and Android. The PR carries iOS and Android screenshots, taken by hand with the API stopped, of the connection error with "Thử lại" and of the list after a retry.

## Out of scope

- Pull to refresh, automatic retry, or a reload when the app returns to the foreground.
- A retry on the web.
- Any API or shared-schema change.
- A general handler for a rejected session; that is #31, which merges after this issue.
- A Maestro flow for the loading or retry states.

# Plan: Mobile: joining from an invite link opens the group's own screen

Issue: #112 · Spec: [112.md](112.md) · Runs on: `cloud, then mac` · Status: waiting for gate 2

## Contracts

None. No HTTP, schema or migration changes, and `packages/shared` stays as it is.

The screen already has what it needs: `joinMyInvite` returns `JoinOutcome`, and `{ kind: "joined", group }` carries the group with its `id`. The API already promises that joining as a member changes nothing, and tests it: `#94 AC 3` in `apps/api/src/groups/store.contract.ts` (the store) and `apps/api/src/groups/routes.test.ts` (the route, which also checks the member count stays 2).

## What the code does today

Read in full: `invite-screen.tsx`, `invite-screen.test.tsx`, `lib/invites.ts`, `lib/pending-invite.tsx`, `group-screen.tsx` (its first 125 lines and every `testID`), `app/_layout.tsx`, `packages/shared/src/groups/flow.ts` and the invite Maestro flows.

- `invite-screen.tsx` navigates to the groups list in two places, both `router.replace("/")`: line 49 for a member (the preview says `alreadyMember`) and line 71 after a join. `grep -rn 'replace("/")' apps/mobile/src` finds only these two in non-test code.
- A member's preview has no group id, and the join call returns it. So for a member the screen has to make the join call itself. That is a new async step on open, after the preview, and it needs the same protection against a second link arriving as the preview already has.
- The group screen (`/groups/[id]`) shows `group-screen`, `group-title`, the expenses and `add-expense`. It shows **no member count**. The IDs `group-name` and `group-member-count` belong to the groups-list rows in `app/index.tsx`.
- Three Maestro flows open an invite and then assert those list-row IDs: `invite-open.yaml`, `invite-member.yaml` and `invite-signed-out.yaml` (`grep -l 'group-name\|group-member-count'` over the flows that call `open-invite`). The spec's matrix names the first two. All three would fail once the group screen opens, so all three change.
- After sign-in, the home screen sends a visitor to the invite with a `Redirect` (`usePendingInviteHref`), so the invite is the only screen in that stack. After a join, the group screen would have nothing under it there. In a warm app the groups list is under the invite, so Back returns to it.

## Risks

- **The spec asks for something the group screen can't show.** Its matrix says the group screen "shows its name and 2 members", but the group screen has no member count. The plan reads it as: the group screen opens (name, expenses), and the count is checked on the list after going back. In `invite-signed-out` there is nothing to go back to, so it only checks that the group screen opens, which already proves membership because a non-member gets a 404 for `GET /groups/:id` (`[security] #97 AC 11` in `apps/api/src/groups/routes.test.ts`). Question for the author: is that reading right?
- **Back after joining.** With one `replace`, as the issue describes, a visitor who came from sign-in, or from a link that started the app, has no list under the group screen. Back then leaves the app on Android or has nowhere to go on iOS, where today the groups list is always there. The alternative is to open the list first and then the group (`replace("/")`, then `push`), so Back always works, at the cost of a second navigation. The plan follows the issue and uses one `replace`. Question for the author: is that acceptable?
- **A member's open now makes one more call.** It joins, which the API turns into a no-op for a member (`#94 AC 3`). The new rule that the screen joins by itself only for a member is guarded by the step 1 test; if it were inverted, a non-member would join without pressing the button.
- **A join the member pressed, resolving after a second link replaced the screen.** It still opens the group they joined. That is unchanged behavior and is not tested here.
- **`replace` from an async continuation.** #98 found that a `router.replace` made from an effect raced the root layout's guard at sign-in. Here the `replace` follows a user press or a loaded preview, not the sign-in itself, and `invite-signed-out` and `invite-member` exercise both; if one is lost on a platform it shows in step 4.
- **Open PR #117** changes `group-screen.tsx`, its test, `CLAUDE.md` and `REVIEW.md`. None of those is a file this plan changes, and the plan only relies on the group screen's `group-screen` and `group-title` test IDs. Either can merge first. If #117 renames those IDs, step 4's flows fail loudly.
- **The step 4 fail-first run costs an extra iOS Release build** (several minutes). If the Mac session can't afford it, the unit tests still carry the test-first proof, and the PR says the flows were not run against `main`.
- **Left as it is:** the branch in `invite-screen.tsx` that returns `null` for `invite.alreadyMember` is already unreachable, because a member's answer is never stored. It is not part of the spec.
- **Rollback:** revert the screen and the flows. No data, API or shared code is touched.

# Balances: each member's balance and the fewest payments to settle, on the API

Issue: #96 · Runs on: `cloud` · Status: waiting for gate 1

## User story

As a member of a group, I want to see each member's balance and the fewest payments that settle the group, so that we know who should pay whom.

## Acceptance criteria

1. Given a group with members A and B
   When A adds an expense of 100000 VND split equally
   Then A's balance is +50000 and B's balance is -50000

2. Given any set of expenses in a group
   When the balances are computed
   Then they are whole VND and add up to exactly 0

3. Given balances that are not all zero
   When the settlement suggestions are computed
   Then following them brings every balance to 0, with at most (number of members with a non-zero balance − 1) payments

4. Given a group with no expenses
   When a member asks for its balances
   Then every member's balance is 0 and there are no suggestions

5. [security] Given a user who is not a member
   When they ask for the group's balances
   Then they are refused, and the answer doesn't reveal whether the group exists

6. [security] Given a call with no session, or with an ended or unknown session
   When it asks for balances
   Then it gets 401 `unauthorized`

7. Given a group id that is not a valid id
   When balances are asked for
   Then the answer is 404 `not_found`, as for a group that doesn't exist

## Assumptions

1. The route is `GET /groups/:id/balances` and answers 200 with every current member of the group, each with a balance (including 0), plus the list of suggested payments (`from`, `to`, `amount` in whole VND), because the issue names the route and the shared-contract rule requires a Zod schema.
2. A member's balance is what they paid minus the sum of their shares, over all the group's expenses, so a positive balance means the group owes them, because criterion 1 shows A (payer) as +50000.
3. Suggestions are deterministic: the same expenses always give the same payments, with ties broken by user id, because tests and clients need a stable answer.
4. A suggestion is a payment from a member with a negative balance to one with a positive balance, with a whole-VND amount greater than 0, because the issue says following them brings every balance to 0.
5. Payments already made are not counted, because recording a payment is seed item 5.
6. The non-member refusal and the invalid-id answer are the same 404 `not_found` that the expense routes use, and the session check uses the same `guardSession` path, because the repo already settles them.
7. The computation is pure functions in `packages/shared` with unit tests, as the domain-logic rule requires, and the route only loads expenses and calls them.

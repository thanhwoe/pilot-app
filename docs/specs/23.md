# Mobile: test the double-tap guard and the reload after a failed first load

Issue: #23 · Runs on: `mac` · Status: waiting for gate 1

## User story

As a maintainer of the mobile app, I want tests for three fixes made late in review of #14 and #19, so that none of them can break again unnoticed.

## Acceptance criteria

1. Given I'm signed in on the app with no groups
   When I type a name and double-tap "Tạo nhóm"
   Then exactly one group with that name is listed, with "1 thành viên"
2. Given the first list load failed
   When the API is back and I create a group
   Then the list shows that group and my other groups
3. [security] Given a groups list or create request is still pending when I sign out
   When I sign in again and that request then answers 401
   Then the new token is still in secure store and the home screen shows

Each test must fail when its own fix is removed: the `inFlight` guard for 1 (the unit test), the reload after a failed first load for 2, the `mounted` check for 3 (commit `df06be9`).

## Assumptions

- The mobile app gets a unit-test runner, because it has none and AC 2 and 3 need one. It is `jest-expo` with `@testing-library/react-native`, because vitest does not handle React Native well and Expo supports jest-expo. `pnpm test` and CI run it with the other packages. Versions are pinned exactly, except Expo packages, which follow `npx expo install`.
- The AC 2 and 3 tests render the real home screen with its own session provider. They fake only the network (the groups, auth and health API clients) and `expo-secure-store` (an in-memory store), so "the new token is still in secure store" is checked against a real store. No production refactor; the only allowed change to production code is a `testID` a test needs.
- AC 1 is a unit test of the home screen: two presses before React re-renders make one create. Maestro can't tap fast enough to beat the re-render: `doubleTapOn` on iOS and a zero-delay repeated tap on iOS and on Android all passed with the guard removed, with one group stored. A Maestro flow still double-taps on iOS and Android, one at a time, and checks that one group shows, also after a relaunch, but it does not prove the guard. It uses an ASCII group name, because Maestro can't type other text on Android.
- AC 2: the first list request answers with a connection error and the next one lists the new group and an existing one. The test checks that both show, so showing only the new group fails it.
- AC 3 has two cases, a pending list request and a pending create request, each answering 401 after the second sign-in.
- Each test is shown to fail with only its own fix removed, then the fix is restored. `git revert 7c31ac7` undoes two fixes at once, so each is removed by hand. The PR carries the failing output.
- No API, shared-schema or web change, because the issue is about mobile tests only.

## Out of scope

- Any behaviour change in the home screen, session or groups code. If a test shows a bug, that is a new issue.
- A Maestro flow for AC 2 and 3: Maestro can't stop the API partway through a flow or hold a request open.
- Tests for other mobile screens (sign-in, sign-out) and unit-test coverage beyond these three fixes.
- A mobile unit-test setup for the web or shared packages.

# Mobile: a failed reload after saving an expense must not invite a second save

Issue: #107 · Runs on: `cloud` · Status: waiting for gate 1

## User story

As a member adding an expense on my phone, I want a failed refresh after a successful save not to make me save the same expense twice, so that my group's list has no duplicates.

## Acceptance criteria

1. Given the group screen with the add form open and a save that the API accepts (201)
   When the reload of the group and its expenses that follows fails (the API is unreachable, or answers with an error other than 401)
   Then the screen still shows the expenses it had, shows the connection error and a way to retry the reload, and the typed values are not offered for a second save as if nothing had been stored

2. Given the case in criterion 1
   When I retry the reload and it works
   Then the new expense is in the list once

3. [security] Given the reload after a successful save answers 401 `unauthorized`
   When the save had succeeded
   Then the session ends and sign-in shows, as everywhere else

## Assumptions

- After the failed reload the add form is closed and its typed values are dropped, because the expense is already stored and the issue says they must not be offered for a second save.
- The expenses already on screen stay visible and the existing connection error and "Thử lại" button show with them, instead of replacing the whole screen, because criterion 1 asks the screen to keep what it had.
- "Thử lại" after such a failure only reloads the group and its expenses and never sends the save again, because the issue's non-goals leave the save request alone.
- A failed first load, with nothing on screen yet, behaves as it does today, because the issue only concerns a reload after a save.
- A second press of "Thử lại" before the next render sends one reload, as it does for a failed first load, because the retry button is the same.

## Out of scope

- Optimistic inserts, offline use, and any change to the save request itself.
- Any API or `packages/shared` change.
- A Maestro flow: the failure can't be produced on a simulator without a fault-injecting API.

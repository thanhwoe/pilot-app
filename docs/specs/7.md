# Sign in on the mobile app with an email one-time code

Issue: #7 · Runs on: `mac` · Status: waiting for gate 1

## User story

As a member of a group, I want to sign in on my phone with a one-time code sent to my email so that I can add expenses on the go without a password.

## Acceptance criteria

### Signing in

1. Given I am signed out
   When I open the app
   Then it shows the sign-in screen, which asks for my email
2. Given I am on the sign-in screen
   When I submit a valid email
   Then the API is asked for a code for that email, and the screen asks for the 6-digit code sent to that email
3. Given I am on the code step
   When I submit the right code
   Then I am signed in and the app shows the home screen
4. Given I am on the code step
   When I submit a wrong code
   Then I stay signed out, stay on the code step, and see the wrong-code error
5. Given I am on the code step
   When I choose "Dùng email khác"
   Then I am back on the email step
6. Given I am on the sign-in screen
   When I submit a value that is not a valid email
   Then I see the invalid-email error, stay on the email step, and no code is requested
7. Given I already asked for 5 codes for one email in the last 15 minutes
   When I submit that email again
   Then I see the too-many-requests error and stay on the email step
8. Given the API cannot be reached, or does not answer within 5 seconds
   When I submit my email or my code
   Then I see the connection error and stay signed out

### Signed in

9. Given I am signed in
   When I am on the home screen
   Then it shows my email
10. Given I signed in
    When I close and reopen the app
    Then I am still signed in and the home screen shows my email
11. Given I am signed in and the API cannot be reached
    When I open the app
    Then I stay signed in, and the home screen shows the connection error and the sign-out button

### Signing out

12. Given I am signed in
    When I sign out
    Then the app ends my session on the server (it sends my token to the API's sign-out) and shows the sign-in screen
13. Given I signed out
    When I close and reopen the app
    Then it shows the sign-in screen
14. Given I am signed in and the API cannot be reached
    When I sign out
    Then the stored token is deleted and the app shows the sign-in screen

### Security

15. [security] Given I signed in
    When the app stores my session
    Then the token is saved only in the device's secure storage, and is never shown on screen
16. [security] Given the app holds a token the API no longer accepts (expired, signed out elsewhere, or made up)
    When I open the app
    Then it shows the sign-in screen and the stored token is deleted
17. [security] Given I am on the code step
    When I submit a code that is not exactly 6 digits
    Then I see the code-format error, stay signed out, and no sign-in is attempted
18. [security] Given I used up the 5 attempts on a code
    When I submit the right code
    Then I see the same wrong-code error as for any other wrong code, and stay signed out

### Shared with the web

19. Given the web sign-in from #6
    When its copy, error mapping, step logic and API client come from the shared package instead of `apps/web`
    Then the web's Playwright tests pass without changes, and the web keeps no second copy of the moved parts
20. Given the moved parts in the shared package
    When the web and mobile apps use them
    Then both apps show the same Vietnamese copy for the same outcome, and the shared unit tests cover every outcome (success, invalid email, code format, wrong code, too many requests, connection error, timeout)

## Assumptions

- The decisions and assumptions from #5's intake apply: the token is opaque, sessions last 30 days, and the API returns the same 401 for wrong, expired, used and never-requested codes.
- The behaviour and Vietnamese copy match the web from #6 wherever the issue doesn't say otherwise, including no resend button and the same exact strings (listed in [6.md](6.md)).
- The token is kept only in `expo-secure-store`, as the issue says. It is never logged or put in a URL or an error message.
- At app start with a stored token, the app calls `GET /me`. 200 shows home, 401 deletes the token and shows sign-in, and an unreachable API keeps the session (the web's gate-2 decision in #6).
- Sign-out deletes the stored token even if the API call fails, because a user who asks to sign out must end up signed out on this phone.
- Shared step logic takes plain values (`{ email }`, `{ email, code }`), not `FormData`, because mobile has no forms. The web's Server Actions turn `FormData` into those values.
- The shared API client takes its base URL as an argument. The web keeps `API_URL`; mobile keeps `EXPO_PUBLIC_API_URL`, or `localhost` on iOS and `10.0.2.2` on Android.
- The 5-second timeout uses `AbortController` with `setTimeout`, not `AbortSignal.timeout`, because React Native may not support the latter and both apps need the same behaviour.
- Cookies, Server Actions and the proxy are Next-only and stay in `apps/web` (author's answer at intake). The web's unit tests for the moved parts move to `packages/shared`.
- The code field uses a numeric keyboard and one-time-code autofill. Every element the Maestro flows use has a `testID`, as `CLAUDE.md` asks.
- Maestro runs both platforms on the Mac mini only, not in CI (author's answer at intake). Running it in CI on the `macos-sim` runner is a separate issue.
- Maestro runs a Release build made with `npx expo run:ios` / `run:android` (Continuous Native Generation), so "close and reopen" really restarts the app and no Metro or dev menu is involved. The generated `ios/` and `android/` folders stay out of git. Flows launch the app by its id, `com.thanhwoe.gop`.
- The flows sign in through `GET /dev/sign-in-code` against a local API with `NODE_ENV=test` and `DEV_SIGN_IN_CODES=true`. Each flow uses its own email, because the API limits codes per email.

Why some criteria are `unit` or `manual` only:
- AC 8, 11 and 14 need an API that is down or hangs, and AC 16 needs a token the API rejects. Maestro can't stop the API mid-flow or write to the secure store.
- The decision each one needs is shared logic, so unit tests with a fake API and a fake store prove it.
- AC 11 also needs iOS and Android screenshots of the API-down home in the PR, taken in the verify step.

## Out of scope

- Any API change beyond what #5 provides.
- Biometrics, push notifications, and managing other sessions.
- Running Maestro in CI, including on the `macos-sim` runner (a separate issue).
- Remembering the email, a resend button or countdown.
- Changing the web's behaviour or copy. The web only changes where it imports the moved parts from.

# CI: the iOS step of Mobile E2E fails on the macos-sim runner (osascript System Events)

Issue: #109 · Runs on: `mac` · Status: waiting for gate 1

## User story

As the owner reviewing mobile PRs, I want the `Mobile E2E` job to run the iOS Maestro flows on the `macos-sim` runner, so that a PR's iOS evidence comes from CI and not only from a local run.

## Acceptance criteria

1. Given a same-repo PR that touches `apps/mobile/**`
   When the `Mobile E2E` workflow runs on the `macos-sim` runner
   Then the `Maestro flows on iOS` step builds the app, launches it on the iPhone 16 Simulator and runs every flow in `.maestro`

2. Given the runner has been fixed
   When PR #108 (or any mobile PR) has its failed job re-run
   Then the `mobile-e2e` job is green on both iOS and Android

3. Given the runner user has not been granted Automation permission for System Events
   When the iOS run builds, installs and starts the flows
   Then no step needs System Events (`osascript`) and the iOS step does not wait on a permission prompt

4. Given the same `e2e:ios` command
   When it runs on a local terminal or on the runner
   Then both use the same simulator, build and install path

## Assumptions

1. The cause is most likely a permission prompt on the runner after its self-update, but this is not confirmed and doesn't need to be, because the fix removes the repo's dependence on it (owner comment).
2. The simulator is booted with `xcrun simctl`, the Release app is built without `expo run:ios`'s launch step, it is installed with `xcrun simctl install`, and the Maestro flows launch the app as they already do. The plan picks the exact commands.
3. "iPhone 16" stays the simulator, as `run.sh` uses today.
4. Criterion 2 is checked by re-running #108's `mobile-e2e` job after this issue's own PR shows a green run. The machine's Automation settings stay untouched until then.
5. The Android path is unchanged.

## Out of scope

- Changing any Maestro flow or any app code.
- Granting the Automation permission by hand on the Mac mini.
- Changes to the runner machine beyond what the repo's script and workflow do.

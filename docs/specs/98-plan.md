# Plan: Mobile: open an invite link in the app and join the group

Issue: #98 · Spec: [98.md](98.md) · Runs on: `cloud, then mac` · Status: waiting for gate 2

## Contracts

None. No migration, no endpoint, no schema and no copy change: #94 already added the invite calls (`previewInvite`, `joinWithInvite`), the flow functions (`openInvite`, `acceptInvite`, `isInviteSignedOut`), `inviteTokenSchema` and `invitesCopy` to `packages/shared`, and the mobile app's `groupsApi` is built from `createGroupsApi`, so it has them.

Two things are new, both inside `apps/mobile`:

- **The link.** `gop://invite/<token>`. The app's scheme is already `gop` in `app.config.ts`, and Expo Router turns the link into the path `/invite/<token>`, so a file route `invite/[token]` is the whole deep-link configuration. No change to `app.config.ts`.
- **A pending invite.** An in-memory holder for the token of an invite that a signed-out visitor opened, so that after sign-in the app goes back to it. It keeps a token only if `inviteTokenSchema` accepts it.

## What the code does today

Read in full: `apps/mobile/app.config.ts`, `src/app/{_layout,sign-in,index}.tsx`, `src/lib/{session,groups,api,session-guard}.ts(x)`, `tsconfig.json`, `tsconfig.test.json`, the first 90 lines of `src/home.test.tsx`; in `packages/shared`: `groups/flow.ts` and `groups/api.ts` (the invite functions), `groups/copy.ts`; the web's `lib/return-path.ts` and `invite/invite.tsx` for what "the same error as the web" means; `.maestro/subflows/*.yaml` and `scripts/dev-code.js`.

- **The layout hides screens by session.** `RootStack` renders nothing while the session loads, then a `Stack` with `index` under `Stack.Protected guard={signedIn}` and `sign-in` under `guard={!signedIn}`. `signedIn` is `state.kind !== "clear"`, so a session the API could not be asked about still counts as signed in. A signed-out visitor who is sent to a protected screen lands on `sign-in`, and the address they asked for is lost. That is why the invite route is not placed under either guard: its screen decides.
- **Sign-in changes screens by itself.** `sign-in.tsx` calls `session.signIn` and, on success, does nothing: the guard flips and `index` shows. There is no return address, so the return has to be done where the guard flips, not in the sign-in screen, which unmounts at that moment.
- **The invite logic exists.** On the web, `Invite` calls `openInvite`, sends a member to the list, shows `invitesCopy.badLink` for `bad-link` and `groupsCopy.unavailable` for any other failure, and `JoinForm` calls `acceptInvite`. The mobile screen follows the same states.
- **Deep links and the guard.** I could not find Expo Router documentation in the repo or `node_modules`, so the behaviour of a link that arrives while the session is still loading (a cold start) and while signed out is **not known from the code I read**. The plan treats it as something to prove on the Simulator and the emulator (step 3 and 4), and the design does not depend on the answer: the invite route is always registered, and the screen waits for the session.
- **Expo Router under Jest.** Tried earlier in the cloud: with `jest-expo`, `jest.spyOn(router, "replace")` works with no router mounted, and `useLocalSearchParams()` returns `{}`. So screens are rendered as components with the token as a prop.
- **Typed routes.** `experiments.typedRoutes` is on, but `.expo/types` is generated by `expo start` and is not in the repo, so in the cloud `router.replace` takes a plain string. On the Mac the generated types may exist and accept `` `/invite/${token}` ``, because the route will exist.
- **Whole-shape tests and flows.** `grep -rn "Stack.Screen\|Stack.Protected" apps/mobile/src` finds only `_layout.tsx`, which has no test. The existing Maestro flows (`01-signed-out.yaml` to `18-locked-code.yaml`, `groups-*.yaml`) start signed out and expect `sign-in`; adding a route that is always registered could change where a cold start lands, so step 3 runs the whole set on both platforms, not only the new flows.
- **Open PRs.** `gh api repos/{owner}/{repo}/pulls` returns none. See Risks for the branch `feat/97-mobile-group-expenses`, whose plan touches the same layout.

## Risks

- **A question, not a blocker.** After #97 lands, the app has a screen for one group. The spec says joining opens the groups list because that screen does not exist yet. Should joining open the group's own screen once it does? I left it out, as the spec does; it would be a small change in the screen's `router.replace`.
- **Cold start and a protected stack.** I could not confirm from the repo how Expo Router keeps a link that arrives while the layout still renders nothing (the session is loading). Step 4's cold-start flow is the proof. If it fails, the fix is likely to render the stack while loading, or to read the initial link with `expo-linking`, and that is a plan change, not something to improvise.
- **iOS asks before opening a custom scheme.** The Simulator may show an "Open in Góp?" dialog. The subflow taps it when it is visible; the exact wording is found when the flow runs, and a different text on the Android emulator is handled with `when: platform`.
- **In-memory only.** The pending invite lives in memory, so if the app is killed in the middle of signing in, the invite is forgotten and the visitor lands on the groups list. The link still works if they open it again.
- **Same files as #97.** The plan for #97 (`feat/97-mobile-group-expenses`, no PR yet) also edits `_layout.tsx` (a `groups/[id]` screen) and adds Maestro flows and a setup script. The edits are on neighbouring lines and new files, so whichever merges second merges `main` into its branch. Nothing here depends on #97.
- **The spec has no row for its sixth assumption** (the invite calls go through `guardSession`, and a rejected session ends the session). Step 2 tests it anyway (`[security]`, A6); I suggest adding the row at the next spec revision.
- **No retry on a connection error.** Like the web, the screen shows `groupsCopy.unavailable` and nothing else when the preview fails for another reason than a bad link; opening the link again retries. The spec asks for nothing more.
- **Rollback.** Revert the commits. No data, API or config is touched; the route and the in-memory holder disappear with them.

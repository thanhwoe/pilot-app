# Plan: Sign in with an email one-time code: API

Issue: #5 · Spec: [5.md](5.md) · Runs on: `cloud` · Status: waiting for gate 2

## Contracts

### Shared schemas (`packages/shared/src/auth.ts`)

| Schema                        | Shape                                                                                     |
| ----------------------------- | ----------------------------------------------------------------------------------------- |
| `emailSchema`                 | string, trimmed and lower-cased, valid email, at most 254 characters                      |
| `requestCodeBodySchema`       | `{ email }`                                                                               |
| `signInBodySchema`            | `{ email, code }`, `code` exactly 6 digits                                                |
| `userSchema`                  | `{ id: uuid, email }`                                                                     |
| `signInResponseSchema`        | `{ token: string, user: User }`                                                           |
| `meResponseSchema`            | `User`                                                                                    |
| `errorResponseSchema`         | `{ error: "invalid_request" \| "invalid_code" \| "too_many_requests" \| "unauthorized" }` |
| `devSignInCodeResponseSchema` | `{ code: string }`                                                                        |

### Endpoints

| Method and path                | Request                         | Responses                                                                                            |
| ------------------------------ | ------------------------------- | ---------------------------------------------------------------------------------------------------- |
| `POST /auth/code`              | `requestCodeBodySchema`         | 204 empty · 400 `invalid_request` · 429 `too_many_requests`                                          |
| `POST /auth/sign-in`           | `signInBodySchema`              | 200 `signInResponseSchema` · 400 `invalid_request` · 401 `invalid_code` (one body for every failure) |
| `GET /me`                      | `Authorization: Bearer <token>` | 200 `meResponseSchema` · 401 `unauthorized`                                                          |
| `POST /auth/sign-out`          | `Authorization: Bearer <token>` | 204 empty · 401 `unauthorized`                                                                       |
| `GET /dev/sign-in-code?email=` | query `email`                   | 200 `devSignInCodeResponseSchema` · 404 when disabled, in production, or no code was sent            |

`GET /health` does not change.

### Migration `0000` (first one, generated by `db:generate`)

| Table           | Columns                                                                                                                                                  |
| --------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `users`         | `id` uuid PK default `gen_random_uuid()`, `email` text unique, `created_at` timestamptz                                                                  |
| `sign_in_codes` | `id` uuid PK, `email` text, `code_hash` text, `attempts` int default 0, `created_at`, `expires_at`, `used_at` nullable; index on (`email`, `created_at`) |
| `sessions`      | `id` uuid PK, `token_hash` text unique, `user_id` uuid FK → `users` on delete cascade, `created_at`, `expires_at`                                        |

Codes stay in `sign_in_codes` after they are used or replaced, so the 15-minute request count (AC 20) can read them. Only the newest code per email is usable.

### Config (`apps/api/src/env.ts`, `.env.example`)

- `NODE_ENV`: `development` | `test` | `production`, default `development`.
- `DEV_SIGN_IN_CODES`: `true` | `false`, default `false`. The dev endpoint is on only when this is `true` **and** `NODE_ENV` is not `production`.
- `AUTH_SECRET`: required, at least 32 characters. The key for hashing codes and session tokens (HMAC-SHA256), so a copy of the database alone can't be used to recover a live code. `.env.example` holds a placeholder and says how to generate a real one.

## Risks

- **`pnpm test` now needs Postgres locally.** The API tests fail with a clear message when the database is down. `CLAUDE.md` says to run `pnpm db:up` first. CI has a Postgres service already.
- **First migration.** It only adds tables, so no existing data is touched. To roll back: revert the PR and drop `users`, `sign_in_codes` and `sessions` (there is no production database yet). Nothing applies migrations automatically; developers run `db:migrate` after pulling.
- **`buildApp` signature changes.** `app.test.ts` and `server.ts` change with it. `/health`, the web app and the mobile app are unaffected.
- **Concurrent sign-in attempts.** Two requests with the same code could both pass. Checking and consuming a code happens in one transaction that locks the code row, so only one wins; the contract suite tests this.
- **`AUTH_SECRET` is new and required** (decided at gate 2, beyond the spec). A 6-digit code has a million values, so a plain hash could be reversed by anyone holding a copy of the database; a keyed hash can't be without the secret. Existing `apps/api/.env` files need the variable, or the API refuses to start with a clear error naming it. Changing the secret invalidates every live code and session, which is also how to sign everyone out.
- **Dev codes live in API memory.** They're cleared on restart, and only kept when the endpoint is on.
- **Limits are per email only** (spec, out of scope): someone can request codes for many emails and fill the log. Nothing is emailed, so the cost is log noise.

# One handler for a rejected session on every API call

Issue: #31 · Runs on: `cloud` · Status: waiting for gate 1

## User story

As a signed-in member, I want any screen that gets a 401 from the API to send me to sign-in, so that I'm never stuck on a retry message as more screens are added.

## Acceptance criteria

### Shared

1. Given a call that sends my session token answers 401 `unauthorized`
   When its result goes through the shared handler, whichever call it is (the groups list, the group create, or one added later with no 401 handling of its own)
   Then the result is "signed out", not an error message
2. [security] Given a call that sends my session token answers anything except 401 `unauthorized`: 400 `invalid_request`, 404 `not_found`, 429 `too_many_requests`, a 5xx, a timeout, a network failure or a body that isn't valid
   When its result goes through the shared handler
   Then the result is never "signed out": it is the call's own result (the connection error, or the form's own error such as "Hãy nhập tên nhóm.")

### Web

3. Given my session has ended on the API
   When a Server Action's authenticated call answers 401 `unauthorized`
   Then the session cookie is deleted and I land on the sign-in page
4. Given my session has ended on the API
   When a Server Component's authenticated call answers 401 `unauthorized`
   Then I land on the sign-in page and the session cookie is gone
5. Given the API is unreachable, times out or answers with a server error
   When an authenticated call on the web fails that way
   Then the screen shows "Không kết nối được máy chủ. Hãy thử lại." and the session cookie is still there

### Mobile

6. Given my session has ended on the API
   When an authenticated call on the mobile app answers 401 `unauthorized` while the screen that made it is showing
   Then the stored token is deleted and the sign-in screen shows
7. Given the API is unreachable, times out or answers with a server error
   When an authenticated call on the mobile app fails that way
   Then the screen shows "Không kết nối được máy chủ. Hãy thử lại." and the stored token is still there
8. [security] Given an authenticated call is still pending when I sign out
   When I sign in again and that call then answers 401 `unauthorized`
   Then the new token is still in secure store and the home screen shows

## Assumptions

1. "Authenticated call" means a call that sends the session token: `GET /me`, `GET /groups`, `POST /groups` and sign-out. The sign-in calls (request a code, sign in) are not authenticated, because a rejected code is not an ended session. Their behaviour and tests don't change.
2. Sign-out stays as it is: it clears this device whatever the API answers, so a 401 to sign-out changes nothing.
3. Only 401 `unauthorized` ends the session (criterion 2). That includes a 404 `not_found` for a group I'm not in.
4. What #19 made visible doesn't change on either app: its tests, and the #23 mobile tests, pass unchanged. The new proof is that a call added later gets the sign-out with no 401 handling of its own (criterion 1).
5. On the web, a Server Action deletes the cookie and redirects to `/sign-in`. A Server Component redirects to the fixed `/session/clear` route, because it can't change cookies. That route reads no query and always redirects to `/sign-in`, so a link to it can only sign this browser out.
6. The "signed out" result is an internal TypeScript type in `packages/shared`, not a request or response body, so it needs no Zod schema. There is no API change and no new copy.
7. No screen changes, so there are no screenshots and no Maestro flow. Maestro can't make the API answer 401 mid-flow (#19). The web end-to-end tests run in the cloud only when the environment allows Playwright's browser hosts, otherwise in CI.

## Out of scope

- Any API change.
- A "your session expired" message on the sign-in screen.
- A Maestro flow for a 401, because Maestro can't produce one (assumption 7).
- Changing the sign-in calls, sign-out, token refresh or retry.
- New screens that make authenticated calls (expenses, invites, settlements): this issue only makes them cheap to add.
- Any change to the copy of the connection error.

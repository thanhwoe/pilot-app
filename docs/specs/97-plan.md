# Plan: Mobile: a group's expenses, and adding one with an equal split

Issue: #97 · Spec: [97.md](97.md) · Runs on: `cloud, then mac` · Status: waiting for gate 2

## Contracts

No migration. No new endpoint. One response grows, and the shared package gains the pieces the mobile screen needs.

- **`GET /groups/:id`** answers `200` with a new `groupDetailResponseSchema`: the existing group fields (`id`, `name`, `memberCount`, `createdAt`) plus `members: { userId: uuid, email: string }[]`, in the order `listMembers` gives (joined, then user id). `POST /groups`, `GET /groups` and the join answer keep their shapes. `401 unauthorized` and `404 not_found` (a non-member, an unknown id and a malformed id, all the same body) are unchanged, and the body holds a member's email only for a member.
- **`AuthStore.findUsersByIds(ids): Promise<User[]>`** (internal): the route joins the members with their users, so the group store never holds an email.
- **Signed-in state gets the user's id.** `AccountState`'s signed-in case, `submitCode`'s and `completeSignIn`'s success answers, and the mobile session's signed-in state all carry `userId` next to `email`. `/me` and the sign-in response already return it. The web ignores it.
- **`GroupsApi` gains** `getGroup(token, groupId)` (`GET /groups/:id`), `listExpenses(token, groupId)` (`GET /groups/:id/expenses`) and `createExpense(token, groupId, body)` (`POST /groups/:id/expenses`), parsed with `groupDetailResponseSchema`, `expenseListResponseSchema`, `createExpenseBodySchema` and `expenseResponseSchema`, which #95 already added. Two flow functions use them and read a 401 through `guardSession`: `loadGroupScreen` (the group, its members and its expenses) and `submitExpense` (checks the form with the shared schema, then saves).
- **Pure functions in `packages/shared`** (`expenses/format.ts`): `formatVnd(amount)` gives `90.000 ₫`; `formatAmountInput(text)` keeps digits only, at most 9, with `.` between groups of three; `parseAmountInput(text)` gives the integer (0 for an empty field); `formatExpenseDate(createdAt, utcOffsetMinutes)` gives `dd/MM/yyyy` in the given offset, so the screen passes the device's and tests pass their own; `payerLine(payerId, myId, members)` gives the line under a description.
- **Copy** (`expensesCopy` in `packages/shared`, next to `groupsCopy` and `invitesCopy`, every string pinned by a test): see the table at the end of the steps.
- **Mobile route** `groups/[id]`, a screen under `src/app/groups/[id].tsx` that only reads the id and renders the screen component, which lives outside `src/app` so its test can too (Expo Router bundles every file in `src/app`).

## Risks

- **Question for the author. Answer this before adding `plan-ok`; the build reads the answer.** Is the wording in the copy table right? Three strings are mine: the fallback `Thành viên khác đã trả` (needed so a payer who is not in the members still shows something), the amount-limit message that spells the limit, and `Lưu` for save.
- **Emails reach other members.** `GET /groups/:id` now sends every member's email to every member. The owner decided this (there are no display names). The `[security]` test in step 3 pins that a non-member, an unknown group and a malformed id get no email, and that a member sees only their own group's emails.
- **An id with no user is an error.** A member row always has a user (a foreign key), so the case cannot occur in Postgres. If it ever did, the route fails instead of leaving the member out, because a missing member would drop out of the split without anyone noticing.
- **A stale member list.** The screen splits between the members it loaded last. A member who joins while the screen is open is not in the split until it reloads. The API accepts the shorter list, so nothing breaks; the spec says so (assumption 6).
- **The Maestro setup script is new.** It makes a second user and an expense through the API, which no flow does yet; the existing scripts only read a code or send code requests. It uses the dev code endpoint, which the e2e run has on. Each flow uses a fresh email, and each user stays under the API's 5 codes per 15 minutes (the first user signs in through the app and once more in the script; the second signs in once).
- **iOS back and Maestro.** The flow's way back from the group screen on iOS (the header's back button) is not known until the flow runs on the Simulator. Step 8 says to find it there and, if a command differs by platform, use `when: platform`.
- **`AccountState` is shared with the web.** The web reads only `kind` and `email`, so the extra field changes nothing there; the web unit tests and one e2e run show it.
- **Release build and test files.** The group screen's tests live in `src/`, outside `src/app`, as `CLAUDE.md` requires, and the `expo export` bundle in steps 6 and 7 is what the CI `check` job runs.
- **Open PRs:** none. This builds on #95 (expenses API), #94 (members can join, so a group can have several) and #96's list item type.
- **Rollback.** Revert the commits. No migration and no data change; the extra `members` field in `GET /groups/:id` is read by nothing else, and the extra `userId` is ignored by the web.

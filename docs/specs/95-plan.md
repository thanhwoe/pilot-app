# Plan: Expenses: add and list expenses with an equal split, on the API

Issue: #95 · Spec: [95.md](95.md) · Runs on: `cloud` · Status: waiting for gate 2

## Contracts

New shared module `packages/shared/src/expenses.ts` (schemas and constants) and `packages/shared/src/expenses/split.ts` (the pure split), exported from `packages/shared/src/index.ts` the way `groups` is. No client (`createExpensesApi`) yet: no screen calls these routes until #97.

- **Constants.** `EXPENSE_AMOUNT_MIN = 1`, `EXPENSE_AMOUNT_MAX = 100_000_000`, `EXPENSE_DESCRIPTION_MAX_LENGTH = 200`, in `expenses.ts` next to the other shared limits (`GROUP_NAME_MAX_LENGTH` is in `groups.ts`).
- **`createExpenseBodySchema`**, the body of `POST /groups/:id/expenses`: `{ payerId: uuid, amount: integer 1..100000000, description: trimmed string, 1..200, splitBetween: uuid[] }`. `splitBetween` has at least one entry and no repeats. `z.int()` rejects 0.5 and `NaN`; a number below 1 or above the maximum is rejected by the range.
- **`expenseSchema`** and **`ExpenseResponse`**: `{ id: uuid, groupId: uuid, payerId: uuid, amount: integer, description: string, createdAt: ISO datetime, shares: { userId: uuid, amount: integer ≥ 0 }[] }`. `shares` is ordered by `userId`, ascending, so both stores and every client see one order. A member of the split who ends up with 0 VND (1 VND between three members) still has a share row of 0; a payer outside the split has none (AC 3).
- **`expenseListResponseSchema`** `{ expenses: Expense[] }`, newest first.
- **Endpoints.**

  | Method and path             | Request                   | Success                           | Errors                                                     |
  | --------------------------- | ------------------------- | --------------------------------- | ---------------------------------------------------------- |
  | `POST /groups/:id/expenses` | `createExpenseBodySchema` | `201` `ExpenseResponse`           | `400 invalid_request`, `401 unauthorized`, `404 not_found` |
  | `GET /groups/:id/expenses`  | none                      | `200` `expenseListResponseSchema` | `401 unauthorized`, `404 not_found`                        |

  Error bodies are the existing `ErrorResponse` ones. A non-member and an unknown or malformed group id get the same `404 not_found`. The order of checks on both calls is: session (401), then group id and membership (404), then the body (400), then that the payer and the split are members (400).
- **Pure function.** `splitEqually({ amount, payerId, members })` → `{ userId, amount }[]`, where `members` are the split's members as `{ userId, joinedAt }`. Each share is `floor(amount / n)`. The remainder (`amount mod n`, at most `n − 1`) goes 1 VND at a time to the payer if in the split, then to the others by `joinedAt`, then `userId` (compared as strings; uuids are lower-case hex, so this is the byte order Postgres uses). The request order of the members does not matter.
- **Migration** `apps/api/drizzle/0002_*.sql`, generated by `db:generate`. Additive: two new tables, no change to existing ones.
  - `expenses`: `id uuid pk default gen_random_uuid()`, `group_id uuid not null → groups(id) on delete cascade`, `payer_id uuid not null → users(id) on delete restrict`, `amount integer not null`, `description text not null`, `created_at timestamptz not null`, index on `(group_id, created_at)`.
  - `expense_shares`: `expense_id uuid not null → expenses(id) on delete cascade`, `user_id uuid not null → users(id) on delete restrict`, `amount integer not null`, primary key `(expense_id, user_id)`.
  - `integer` holds the 100,000,000 maximum with room (the issue's answer). `restrict` on the users keeps a user's deletion (a feature that does not exist yet) from silently removing other people's money records.
- **Internal interfaces.** `GroupStore` gains `listMembers(groupId): Promise<{ userId, joinedAt }[]>` (by `joinedAt`, then `userId`). A new `ExpenseStore` has `addExpense(expense)` (the expense and its shares in one transaction) and `listExpenses(groupId)`. `AppDeps` gains a required `expenseStore`.

## What the code does today

Read in full: `apps/api/src/groups/{routes,store,memory-store,store.contract,store.test,memory-store.test}.ts`, the first 225 lines of `groups/routes.test.ts` and the `AC 11` block's shape, `apps/api/src/{app,server}.ts`, `auth/session.ts`, `db/schema.ts`, `test/db.ts`, `drizzle.config.ts`, the migration journal and `0001_*.sql`, `packages/shared/src/{groups,index}.ts`, `groups/index.ts` and `REVIEW.md`.

- **Group access is already one check.** Every group route calls `createSessionCheck`, then validates the id with `z.uuid()` and asks `groupStore.findGroupForMember(id, userId)`, answering `404 not_found` for a malformed id, an unknown group and a non-member alike. The expense routes reuse this unchanged. The uuid check matters on Postgres: it rejects a non-uuid id with an error, so the route must not pass one to the store (`groups/routes.test.ts` has a Postgres test for that).
- **Membership order is not available.** `group_members.joined_at` exists, but the store never reads it. The in-memory store keeps members as `Map<groupId, Set<userId>>`, so `addMember(groupId, userId, now)` drops `now`. The remainder rule needs it, so step 2 stores it.
- **Stores come in pairs.** Each store has a Postgres version, an in-memory fake and one contract suite (`store.contract.ts`) run against both, with a Postgres-only block for what the fake cannot show (`store.test.ts`: "saves exactly one membership…"). `createTestDb()` makes a throwaway database with the migrations applied. Route tests use the fake and, for ids, one Postgres test.
- **Callers.** `grep -rn "createMemoryGroupStore\|groupStore:" apps --include=*.ts` finds `buildApp` called with a group store in `auth/dev-codes.test.ts`, `auth/log.test.ts` (2), `auth/routes.test.ts` (2), `app.test.ts` (one shared deps object), `groups/routes.test.ts` and `server.ts`. A required `expenseStore` needs one new line in each; that is plumbing, to keep the repo compiling.
- **`addMember` readers.** `grep -rn "addMember" apps --include=*.ts` finds `groups/store.contract.ts` (the harness type and one call), `groups/memory-store.ts` (definition), `groups/memory-store.test.ts` and `groups/store.test.ts` (the harness). Step 2 changes the fake's internals only; the signature `addMember(groupId, userId, now)` already carries the time and stays.
- **No docs to update.** `grep -rn "/groups\|groupStore" README.md CLAUDE.md REVIEW.md` finds nothing about endpoints or stores. No `.env` or config change.
- **Open PRs.** `gh api repos/{owner}/{repo}/pulls` returns none. See Risks for #87, which plans to edit three of the same files.

## Risks

- **Overlap with #87.** Its plan (branch `feat/87-email-sign-in-codes`, no PR open yet) edits `apps/api/src/server.ts`, `auth/log.test.ts` and `auth/routes.test.ts`, which step 4 touches by one line each. Whichever merges second merges `main` into its branch; the edits are on neighbouring lines of the same `buildApp` calls and should merge by hand in minutes. I propose this PR first, since #96 and #97 build on it; nothing here depends on #87.
- **A zero-VND share.** 1 VND between three members stores shares of 1, 0 and 0. The spec accepts an amount of 1 and says the shares add up, so every member of the split has a row. If you would rather leave zero shares out, say so; it changes the split function's output and the tests in step 1.
- **The list has no paging.** The spec says every expense. A group with thousands of expenses returns them all in one response. Paging is a later issue.
- **The request shape is flat** (`splitBetween` is a list of user ids). When exact-amount and share splits arrive, the body needs a way to say which split it is. There is no client yet, so changing it then breaks nothing, but #96 and #97 will read this shape.
- **Membership is read, then the expense is written.** Nothing can remove a member today, so the two are consistent. When leaving a group exists, the membership read and the insert belong in one transaction.
- **Hiding the group's existence.** Membership is checked before the body, so a non-member who sends an invalid body still gets `404`, the same as for an unknown id, never `400`.
- **Rollback.** Revert the commits and drop the two new tables (`expense_shares`, then `expenses`); the migration touches no existing table, and no deployed environment exists yet.

# Sign in on the web with an email one-time code

Issue: #6 · Runs on: `cloud` · Status: waiting for gate 1

## User story

As a member of a group, I want to sign in on the web with a one-time code sent to my email so that I can use Góp in the browser without a password.

## Acceptance criteria

### Signing in

1. Given I am signed out
   When I open the home page
   Then I am sent to the sign-in page, which asks for my email
2. Given I am on the sign-in page
   When I submit a valid email
   Then the API is asked for a code for that email, and the page asks for the 6-digit code sent to that email
3. Given I am on the code step
   When I submit the right code
   Then I am signed in and sent to the home page
4. Given I am on the code step
   When I submit a wrong code
   Then I stay signed out, stay on the code step, and see the wrong-code error
5. Given I am on the code step
   When I choose "use another email"
   Then I am back on the email step
6. Given I am on the sign-in page
   When I submit a value that is not a valid email
   Then I see the invalid-email error, stay on the email step, and no code is requested
7. Given I already asked for 5 codes for one email in the last 15 minutes
   When I submit that email again
   Then I see the too-many-requests error and stay on the email step
8. Given the API cannot be reached
   When I submit my email or my code
   Then I see the connection error and stay signed out

### Signed in

9. Given I am signed in
   When I open the home page
   Then it shows my email
10. Given I am signed in
    When I open the sign-in page
    Then I am sent to the home page

### Signing out

11. Given I am signed in
    When I sign out
    Then my session ends on the server (its token gets 401 from the API) and I am back on the sign-in page
12. Given I signed out
    When I open the home page
    Then I am sent to the sign-in page
13. Given I am signed in and the API cannot be reached
    When I sign out
    Then the session cookie is removed and I am back on the sign-in page

### Security

14. [security] Given I signed in
    When the session cookie is set
    Then it is `httpOnly` and `SameSite=Lax`, and `Secure` in production (`NODE_ENV=production`) but not outside it
15. [security] Given I signed in
    When the session cookie is set
    Then it expires 30 days after sign-in, the same as the API session
16. [security] Given my browser holds a session cookie the API no longer accepts (expired, signed out elsewhere, or made up)
    When I open the home page
    Then I am sent to the sign-in page and the cookie is removed
17. [security] Given I am on the code step
    When I submit a code that is not exactly 6 digits
    Then I see the code-format error, stay signed out, and no sign-in is attempted
18. [security] Given I used up the 5 attempts on a code
    When I submit the right code
    Then I see the same wrong-code error as for any other wrong code, and stay signed out

## Assumptions

- The decisions and assumptions from #5's intake apply, as the issue says: the session token is opaque, sessions last 30 days, and the API returns the same 401 for wrong, expired, used and never-requested codes.
- The session cookie holds the API's bearer token and is set only on the server, so page scripts never see the token.
- The web talks to the API only from the server, through the existing `API_URL` setting, because the token never reaches the browser. No API change and no CORS change.
- Inputs are checked with the shared email and code schemas before the API is called, and responses are parsed with the shared schemas, because `CLAUDE.md` requires both.
- There's no resend button. "Use another email" goes back to the email step, and submitting the email again sends a new code. A resend countdown is a non-goal.
- If the sign-out call to the API fails, the cookie is still removed, because a user who asks to sign out must end up signed out in this browser.
- The signed-in home keeps the existing API status line under the email and the sign-out button.
- Playwright runs the web end-to-end tests in Chromium only. They sign in through `GET /dev/sign-in-code` from #5, with the API running with `NODE_ENV=test` and `DEV_SIGN_IN_CODES=true`. They run against a production build of the web, which is how criterion 14's `Secure` flag gets tested in a real browser.
- The end-to-end tests run in CI as their own job, so "CI green" covers them. `pnpm test` keeps working without a browser. This changes `.github/workflows/ci.yml`.
- Vitest, the runner the API and shared packages already use, is added to `apps/web` for the unit tests.
- The UI copy is in Vietnamese, like the current pages, and the tests check this exact text:

  | ------------------ | --------------------------------------------------------------- |
  | Email step heading | Đăng nhập                                                       |
  | Email step button  | Gửi mã                                                          |
  | Code step prompt   | Nhập mã 6 số đã gửi tới <email>                                 |

## Out of scope

- Any API change beyond what #5 provides.
- Remembering the email, a resend button or countdown, and managing other sessions.
- Mobile sign-in (#7).
- Browsers other than Chromium in the end-to-end tests.
- Protecting pages other than the home page, since there are no other pages yet.
